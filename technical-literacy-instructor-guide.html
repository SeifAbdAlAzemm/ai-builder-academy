The Logic Machine

البرنامج والمدخلات والمعالجة والمخرجات
4 min · CORE

هدفك

يفهم Software وInput وProcess وOutput، ويقدر يوصف أداة من غير ما يتكلم عن لغة برمجة.

ابدأ بالكلام ده

«تخيل عندك آلة بتدخل فيها حاجة، بتعمل عليها خطوات، وتطلعلك نتيجة. البرنامج شبهها: مجموعة تعليمات وقواعد بتخلي الكمبيوتر يعمل مهمة. زي Excel لما تحط سعر وعدد وحدات، وهو يحسب الإجمالي.»

شرح المصطلحات

Input: البيانات اللي بدخلها، زي السعر والكمية. Process: اللي البرنامج بيعمله، زي الضرب. Output: النتيجة، زي الإجمالي. Business rule: قاعدة من الشغل، زي الكمية لازم تكون رقم صحيح وغير سالب. القاعدة دي إنت بتحددها بخبرتك مش الكمبيوتر من نفسه.

Live Demo — Run the machine

حط Product price = 25 وQuantity = 4. قبل Run process اسأله يتوقع النتيجة؛ المفروض 100. خلي الكمية 2، الناتج 50. جرّب كمية -1 أو 2.5؛ الأداة ترفضها. خليه يشرح ليه الرفض جزء من القواعد. الحساب نفسه مش محتاج AI.

مثال من مجاله

مراجعة عنوان منتج: Input العنوان والحد المسموح، Process عد الحروف ومقارنة الحد، Output مقبول أو يحتاج تعديل. الحد لازم يجي من قواعد الشغل الفعلية، مش رقم نفترضه على Amazon.

خطأ شائع

البرنامج مش لازم يكون تطبيق كبير، والذكاء الاصطناعي مش لازم يكون جوه كل برنامج. ممكن AI يكتب كود آلة حاسبة لكن تشغيلها يعتمد على قواعد ثابتة فقط.

Checkpoint — الإجابة المتوقعة

«لو رفعت ملف منتجات وطلعت قائمة بالسجلات اللي ناقصها SKU، إيه الثلاث أجزاء؟» الملف Input، فحص كل سجل Process، قائمة الناقص Output. اطلب منه مثال مختلف.

انتقال

«عرفنا البرنامج بيعمل إيه، طب هنخلي المستخدم يتعامل معاه إزاي؟»

Choose Your Vehicle

اختيار نوع الحل التكنولوجي
5 min · CORE

هدفك

يميز بين 6 أنواع حلول، ويختار بناءً على المشكلة وطريقة الاستخدام، مش الأداة اللي سمع عنها.

ابدأ بالكلام ده

«لو عايز تروح مشوار قريب، مش لازم تركب طيارة. كل مشكلة ليها وسيلة مناسبة. ممكن تبني موقع أو تطبيق أو إضافة للمتصفح أو Workflow؛ الاختيار مش مسابقة مين الأكثر تطورًا.»

الأنواع الستة

Website: عرض معلومات زي خدمات شركة. Web application: تفاعل وإدخال ومعالجة، زي رفع Excel وفحصه. Mobile app: استخدام على الموبايل أثناء الحركة أو احتياج إمكانيات الجهاز. Browser extension: إضافة بتعيش جوه المتصفح وتساعد أثناء استخدام موقع. Automation workflow: خطوات بتشتغل عند حدث أو في موعد. Desktop app: برنامج محلي على الكمبيوتر، مناسب مثلًا لترتيب الملفات.

Live Demo — Solution selector

اختار Upload a spreadsheet and validate the records وخليه يختار Web application ويبرر. بدّل إلى See a checklist alongside a page in Chrome (Browser extension) وإلى Send a report automatically every morning (Automation workflow). لو الوقت يسمح جرّب Show company services (Website)، Scan items while walking around a warehouse (Mobile app)، Organize local files (Desktop app).

طريقة الاختيار

اسأله: المستخدم فين؟ محتاج واجهة؟ المهمة بتتكرر لوحدها؟ البيانات على الجهاز ولا مشتركة؟ هل محتاج كاميرا أو إشعارات؟ الموقع والتطبيق مش دايمًا فصل حاد: Web App ممكن يشتغل على موبايل، وExtension ممكن تستدعي API، والـ Automation ممكن تبقى جزء من Web App.

خطأ شائع

مش معنى إن حاجة ممكن تتعمل Mobile App يبقى ده أحسن حل. ومش معنى إن البرنامج فيه AI يبقى نوع جديد من الواجهات. AI قدرة ممكن نضيفها لأي نوع.

Checkpoint — الإجابة المتوقعة

«لو عايز تراجع منتج وإنت فاتح صفحة موجودة أصلًا في المتصفح، إيه اختيارك؟» Browser extension غالبًا، بشرط الصلاحيات. ولو مجرد رفع ملف مرة واحدة، Web App أو أداة محلية ممكن تكون أبسط.

انتقال

«دلوقتي اخترنا شكل الحل. تعالى نشوف بيتكون من إيه من جوه.»

Inside the Machine

مكونات التطبيق ورحلة الطلب
5 min · CORE

هدفك

يفهم Frontend وBackend وDatabase وAPI، ويميز بين الواجهة والمنطق والتخزين والتواصل.

ابدأ بالكلام ده

«لما تطلب أكل في مطعم، بتشوف المنيو والصالة، لكن فيه مطبخ بينفذ الطلب ومخزن فيه حاجات. البرنامج الكبير ممكن يبقى شبه كده: اللي إنت شايفه جزء من النظام مش النظام كله.»

شرح المكونات

Frontend زي المنيو: الشاشة والزرار والحقول. Backend زي المطبخ: قواعد الشغل والمعالجة على السيرفر. Database زي مخزن منظم بس للبيانات: يحفظ ويسترجع السجلات. API زي طريقة متفق عليها لتوصيل الطلب والرد بين أجزاء النظام أو بين خدمات مختلفة. التشبيه للتقريب فقط؛ API مش شخص ومش مكان تخزين.

Live Demo — Follow the request

في Sample product name اكتب Blue water bottle. اضغط Start request، ثم Next step في كل مرة. الترتيب: Frontend يجمع الاسم → API request ينقله → Backend يراجع → Database تخزن (محاكاة) → API response يؤكد → Frontend يعرض Saved successfully. بعد كل خطوة اسأله مين المسؤول عنها. Reset يرجع البداية.

مثال من مجاله

في نظام مشترك لإدارة المنتجات: الموظف يدوس Save، الخادم يراجع الحقول والصلاحيات، ويحفظ السجل، ويرجع نتيجة. ولو فيه خدمة AI لاقتراح وصف، التطبيق ممكن يطلبها عبر API منفصل.

خطأ شائع

مش كل Web App محتاج Backend أو Database. عداد الحروف ممكن يشتغل داخل المتصفح فقط. منطق المعالجة ممكن يكون في Frontend أيضًا، لكن قواعد الأمان والصلاحيات في نظام مشترك ما تعتمدش على الواجهة وحدها. رسالة Saved في الديمو مش إثبات تخزين حقيقي.

Checkpoint — الإجابة المتوقعة

«فين الزرار؟ وفين البيانات المحفوظة؟ وإيه اللي ينقل الطلب؟» Frontend، Database في النظام ده، API. «لو غيّرت لون الزرار، هل غيرت قواعد الحفظ؟» مش بالضرورة.

انتقال

«طب الشاشة نفسها بتتبني إزاي؟ هنفصلها قدامك.»

Web Control Room

هيكل وشكل وسلوك صفحة الويب
4 min · CORE

هدفك

يفهم دور HTML وCSS وJavaScript ومصطلحات Source Code وFramework وTech Stack بدون حفظ Syntax.

ابدأ بالكلام ده

«تخيل عربية: جسمها والأجزاء الموجودة فيها حاجة، لونها وتصميمها حاجة، وإمكانية إنك تدوس زرار فتشتغل حاجة تالتة. صفحة الويب في المثال ده برضه ليها محتوى وشكل وسلوك.»

شرح المصطلحات

Source code: الملفات والتعليمات اللي بيتبني منها البرنامج. HTML: هيكل وعناصر ومحتوى الصفحة، لغة markup. CSS: الألوان والمسافات والتنسيق، لغة أنماط. JavaScript: المنطق والتفاعل، لغة برمجة. Python مثال آخر للغة برمجة. Framework: مجموعة أدوات وقواعد بتسهل بناء البرامج. Tech stack: مجموعة التقنيات المستخدمة في المشروع.

Live Demo — Switch off the layers

ابدأ وكل الـ checkboxes شغالة، اضغط Add product مرتين؛ العداد يزيد. شيل CSS، العناصر تفضل موجودة بس التنسيق المخصص يختفي. رجّع CSS وشيل JavaScript؛ الزر ظاهر لكن العداد مش بيزيد. رجّع JavaScript وشيل HTML؛ العناصر تختفي. Reset lab يرجع الحالة. التجربة محكومة؛ صفحات حقيقية ممكن تنشئ عناصر عبر JavaScript وتتفاعل بطرق أخرى.

مثال من مجاله

أداة عد الحروف: HTML فيه خانة العنوان والنتيجة، CSS يخلي التحذير واضح، JavaScript يعد الحروف عند الكتابة. في المثال البسيط مفيش داعي لخادم أو قاعدة بيانات.

خطأ شائع

التصميم الجميل مش دليل إن الوظائف شغالة. HTML وCSS مش لغات برمجة عامة زي JavaScript. مش مطلوب اختيار React أو Python دلوقتي؛ سيب الاختيار لما تعرف الاحتياج.

Checkpoint — الإجابة المتوقعة

«لو عايز تغير لون زرار، هتفكر في إيه؟ ولو الزرار مش بينفذ العملية؟» CSS للشكل؛ JavaScript أو منطق التطبيق للوظيفة، وممكن المشكلة تكون في Backend في نظام حقيقي.

انتقال

«عرفنا الواجهة. طب لو عايزين البيانات تفضل بعد ما نقفل، أو البرنامج يكلم برنامج تاني؟»

Data & Connections

البيانات والتخزين والاتصال
5–6 min · EXTENDED

هدفك

يفرق بين Client وServer، وبين بيانات مؤقتة ومخزنة، ويفهم إن API ممكن يرجع نجاح أو خطأ.

ابدأ بالكلام ده

«لما تفتح موقع من المتصفح، المتصفح ممكن يطلب خدمة من جهاز أو نظام تاني. ولما تقفل الصفحة وتفتحها، مش كل البيانات لازم تفضل موجودة. لازم نختار إيه يتحفظ وفين.»

شرح المصطلحات

Client: طرف بيطلب خدمة، زي المتصفح. Server: طرف بيقدم الخدمة. Temporary state: بيانات عايشة خلال التشغيل. Persistent storage: بيانات بتفضل بعد انتهاء التشغيل بحسب طريقة التخزين. Local storage: تخزين داخل المتصفح، مش قاعدة بيانات مشتركة. Database: تخزين منظم للسجلات. API: واجهة متفق عليها للطلب والرد، وممكن تستدعي خدمة AI أو تسترجع بيانات.

Live Demo — Storage experiment

اكتب Sample A ثم Save temporarily. اكتب Sample B ثم Save locally. اضغط Simulate reload: A تختفي وB تفضل لو التخزين متاح، أو في fallback المحاكاة. ده زر محاكاة مش Reload حقيقي. Clear demo data يمسح البيانات التجريبية. قول إن التخزين المحلي ممكن يتم مسحه ومش بيتشارك تلقائيًا بين الأجهزة.

Live Demo — API request simulator

اكتب P-101 واضغط Send request: هتشوف GET /products/P-101 و200 OK وبيانات Blue water bottle وstock 24. جرّب P-999: 404 Not Found. GET هنا طلب قراءة؛ JSON شكل منظم للبيانات؛ 200 نجاح و404 المورد مش موجود في المثال. دي ردود متبرمجة وليست طلبات شبكة أو Amazon API.

الأمان وخطأ شائع

API مش Database؛ ممكن API يقرأ منها. API Key بيانات اعتماد لازم تتحمى، مش تتحط في كود Frontend ظاهر. النظام الحقيقي ممكن يرجع أخطاء تانية أو يحتاج صلاحيات. تخزين بيانات الشركة أو ربط حسابها يحتاج موافقة، ومش جزء من تجربة النهاردة.

Checkpoint — الإجابة المتوقعة

«لو سجلت منتج على جهازك وعايز زميلك يشوفه من جهازه، هل Local Storage كفاية؟» لا عادة؛ محتاج تخزين مشترك وطريقة وصول آمنة. «404 معناه إيه هنا؟» المنتج المطلوب غير موجود.

انتقال

«عرفنا أجزاء الحل والبيانات. دلوقتي إزاي نبني الحل من غير ما نكون مبرمجين؟»

Builder Toolkit

طرق بناء الحلول وVibe Coding
4–5 min · CORE

هدفك

يميز No-code وLow-code وVibe coding وTraditional coding، ويعرف يكتب وصفًا بسيطًا قابلًا للاختبار.

ابدأ بالكلام ده

«زي ما تقدر تعمل جدول من قالب جاهز أو تفصله بنفسك، تقدر تبني برامج بطرق مختلفة. دلوقتي AI ممكن يكتب الكود بناءً على وصفك، لكن إنت لسه صاحب المشكلة وصاحب قرار هل الحل صح ولا لأ.»

شرح الأنواع

No-code: مكونات مرئية وإعدادات بدون كتابة كود عادة. Low-code: مكونات جاهزة مع كود للتخصيص. Vibe coding: توجيه AI باللغة الطبيعية لتوليد وتعديل الكود، ثم تجربة الناتج؛ مصطلح غير رسمي. Traditional coding: المطور يكتب ويراجع الكود مباشرة وقد يستخدم AI للمساعدة. الطرق دي ممكن تتداخل ومفيش طريقة واحدة دايمًا أفضل.

Live Demo — Build brief generator

املا Problem: Repeated manual title checks. Input: Product title and maximum length. Rules: Count characters; flag empty titles and titles over the configured limit. Expected output: Character count and clear warning. اضغط Create build brief ثم Copy brief. خليه يقرأ الناتج ويغير قاعدة واحدة. ده نص تعليمات، مش برنامج اتبنى ولا اتنشر.

ربط بالـ AI Fundamentals

فيه فرق بين استخدام AI لبناء Software، وبين بناء Software بيستخدم AI أثناء التشغيل. أداة عد الحروف ممكن AI يكتبها من غير AI API؛ أداة توليد وصف ذكي غالبًا تحتاج وصول لنموذج أثناء التشغيل.

خطأ شائع

«اعمل لي برنامج إدارة منتجات» لوحدها مش Requirements كافية. لازم تحدد إيه المدخلات وإيه القواعد وإيه النتيجة ومعيار نجاحها. متدخلش بيانات حقيقية حساسة في الـ prompt.

Checkpoint — الإجابة المتوقعة

«لو AI بنى آلة حاسبة، هل لازم تدفع تكلفة AI كل مرة تجمع فيها رقمين؟» لا؛ طالما البرنامج بيحسب بقواعد محلية ولا يستدعي خدمة AI. «قبل الـ Build تقول إيه؟» المشكلة والمدخلات والقواعد والمخرجات.

انتقال

«لو AI قالك البرنامج خلص، إزاي تتأكد إنه مش مجرد شكل حلو؟»

Bug Hunter

الاختبار وتصحيح الأخطاء والتطوير
5–6 min · CORE

هدفك

يفهم Requirements وPrototype وBug وTesting وDebugging وIteration؛ يتأكد من السلوك قبل الثقة في النتيجة.

ابدأ بالكلام ده

«لو طلبت برنامج يمنع عنوان المنتج الفاضي، والبرنامج شكله ممتاز بس بيقبل عنوان فاضي، هو كده نفذ المطلوب؟ لأ. إحنا هنختبره كأننا المستخدم، مش هنحكم عليه من شكل الشاشة.»

شرح المصطلحات

Requirements: السلوك المطلوب. Prototype: نسخة أولية لتجربة الفكرة. Bug: سلوك غلط مقارنة بالمطلوب. Testing: تجربة حالات مع نتيجة متوقعة ومقارنتها بالنتيجة الفعلية. Debugging: معرفة سبب الخطأ وإصلاحه. Iteration: تعديل وتجربة جديدة. Regression testing: إعادة اختبار الوظائف القديمة بعد التعديل عشان نتأكد إنها ماباظتش.
