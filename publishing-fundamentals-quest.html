Beyond your laptop

Local · Preview · Production

Core · 4 min

Local

Your app runs on your own device. Opening a local HTML file or localhost does not automatically make it available to a colleague.

Preview vs production

A preview is for testing. Production is the environment intended for real users. A preview can also be hosted online.

Server & hosting

A server provides files or runs services. Hosting supplies the environment that makes your application available. Cloud hosting uses provider-managed infrastructure.

Static vs dynamic

A static site can deliver HTML, CSS and JavaScript. An application with server-side logic, shared records or secret API credentials needs suitable managed services or a backend.

Instructor notes

Domain & URL

A domain is a name such as example.com. A URL is the full address, such as https://example.com/tools/checker. Hosting can provide a URL without a custom domain.

DNS & HTTPS

DNS helps resolve a domain to a destination. HTTPS encrypts traffic in transit and authenticates the server using certificates. HTTPS alone does not guarantee a safe application.

MISSION 04 / 08

Time machine

Git · GitHub · Versions

Core · 4 min
⏳
MISSION OBJECTIVEUnderstand version history and how to recover from a bad code change.
+100 XP

Git

Git tracks changes to project files. A commit records a snapshot with a message. A repository contains project files and their history.

GitHub

GitHub hosts Git repositories and supports collaboration. Pushing code to a repository is not necessarily deploying it. Keep private code private and secrets out of commits.

Restore a working versionVERSION HISTORY SIMULATOR
Start at V1: working code.
Offline teaching simulation · No real deployment, service or payment
Important: reverting source code is not the same as restoring a database or redeploying a previous release. Never commit API keys, even in a private repository.
Instructor notes

Commit a feature, introduce a bug, and restore a good snapshot through a new commit. Point out that GitHub and the live app are separate.

Launch control

Build · Deploy · Verify · Rollback

Deployment pipeline

A build prepares the application for its target environment (some apps need no build). Deployment puts a release in that environment. Verification checks what actually runs.

Preview / staging / production

Test in a non-production environment first where possible. Production is for real users. Rollback restores a previous release when compatible; data changes may need a separate recovery plan.

Website / web app

Host online; share an appropriate URL and configure access.

Mobile app

Test on a device; app store or authorized distribution may require signing, review and policies.

Browser extension

Test an unpacked extension locally; store release requires packaging, permission review and policy compliance.

Automation

Run locally or on a managed workflow service; configure triggers, credentials, logs and uptime.

Desktop app

A web app with suitable installability features; may be installed from a browser on supported devices.

Security shield

Core · 5 min

Authentication & authorization

Authentication verifies who a user is. Authorization determines what that user can access. A login page alone does not enforce permissions.

Secrets & privacy

API keys are credentials. Keep secret keys in protected server-side configuration or a provider secret manager, not public JavaScript. Use approved data and minimize access.

Release readiness

A live link is only the beginning. Test requirements, confirm authorized access, protect secrets, and document how the tool works.

Maintenance & ownership

Someone must monitor errors and costs, apply updates, keep backups where needed, and handle user feedback. Know how to pause or recover a broken release.
